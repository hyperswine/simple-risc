# CPU 81 / SDRAM 48 MHz: bridge constraints, placement, pipelined multiply

Kind: experiment record, 2026-11-02. Applies to: HEAD `cf42451` plus the
working tree's bridge-constraint, clock-guard and multiplier changes below.
Follows: [NEXT-STEPS](2026-11-02-NEXT-STEPS.md) item 1,

## Result

The pipeline image closes 81 MHz on the board: vendor gate at 83.075 MHz
(+0.308 ns, 0 setup / 0 hold violations) and `check_processor.py`,
`check_rv32m.py` (30,720 checks) and `check_rv32i.py` (38,400 checks) all
pass on the loaded bitstream (SHA-256 `d9883223f2289b8f...`). All 78
Haskell tests pass. This is an experiment directory, not a preset: no
`fprisc-81` preset is claimed until the full FP-RISC suite runs on it.

## Why 81, not 80

Exactly 80 MHz is unreachable with this PLL/SDC scheme (both divide the
27 MHz crystal by 3-see `dual_pll.v`, `build.sh`). The achievable 80 MHz
class target is **81 = 27x3** (CPU VCO 648 MHz, inside the demonstrated
576-768 MHz range and the 500-1250 MHz VCO check in `build.sh`). The
clock guards in `build.sh` and `sweep_place.py` now admit 81.

## The bridge wall and its fix

The first 81 MHz build (fprisc-72-equivalent settings, placement 0)
failed the gate at 79.239 MHz with 136 setup violations, every worst
path a bridge crossing (`clk_memory -> clk_core`, 0.772 ns closest-edge
relation). 81/48 has a far finer edge beat than 72/48's 6.94 ns, so
single-cycle STA on the CDC payload cannot close at any placement.

The fix is a constraint correction, not a relaxation: `clock_bridge.v`
holds request slots a full round trip and response words from their
write until the next read completes while the CPU side waits two flops
behind the response toggle, so the payload's true relation is two
cycles. `build.sh`'s split-clock SDC now carries `set_multicycle_path
-setup 2 / -hold 1` between the clock pairs (clock-scoped because Gowin
maps the slot and replay arrays to RAM, which reject pin-scoped
constraints; the bridge is the only cross-domain connection and the
synchronizer inputs keep their false paths). The report confirms all
four exceptions `Actived`. Violations went 136 -> 20, all remaining in
the core (BTB RAM loop, cache tag->word, pipeState flops).

## The board rejects the gate-passing image

The place3 image passes `check_processor.py` at 81 MHz but fails
`check_rv32m.py` deterministically: `M FAIL mulhu row 29`, i.e.
`mulhu(0xFFFFFFFF, 0x80000000)`. The control passes: the fprisc-72
bitstream (same RTL HEAD) runs 30,720 checks clean at 72 MHz the same
day. No multiplier path appears in the report's top 25, so STA claims
margin it does not have on the DSP/carry tree: the documented optimism,
this time operand-dependent and deterministic.

## Pipelined DSP combine

`productHalf` summed the four partial products through one 66-bit tree
(34-bit + 66-bit + 66-bit adds plus the slice) in a single M cycle at
`mWait == 1`. It is now two carry chains across two M cycles:
`productMid` latches `((p1 + p2) << 16) + p3` into the new `mSum` slot
field at `mWait == 2`, and `productFinal` adds `(p0 << 32)` and slices
at `mWait == 1`. `mWait`/`e2WaitFast` widen `Unsigned 2` -> `Unsigned 3`
and multiplies wait 4 instead of 3; `productHalf` is kept as their
composition so the exactness property still checks the arithmetic, and
the pipelined half of that property checks the staging. Only
mul/mulh/mulhsu/mulhu take this path (divides hand over to the phases).
Cost: one extra stall cycle per multiply; forwarding still starts at
`mFinal`, so no hazard change. No mirror change: `mSum` lives in the
discarded-together M slot, and the DSP registers stay stable while the
slot is held.

`output/tangnano20k/cpu81-mulpipe` (same place3 options) passes the
gate and all three board suites above. The extra multiply cycle shifts
`Vperf_tb` classifier counts slightly; loop-pricing baselines that
compare against `baseline` should note the new wait.
